# FocusDock 需求合理性分析

## 结论

六项补充需求与最初的菜单栏学习管理方向一致，适合纳入产品，但不能把“应用使用时间”“实际学习时间”“任务完成度”合并成一个指标。推荐的产品模型是：

1. 计划时间回答“准备投入多少时间”。
2. 实际学习时间回答“主动计时或校正后投入了多少时间”。
3. 任务完成度回答“成果推进了多少”，由用户调整。
4. 应用使用时间只提供行为证据，不能自动等同于学习。

## 逐项判断

### 1. 通过应用统计辅助学习时间统计

合理，但只能作为辅助证据。

- VS Code、Anki 或 Preview 在前台，不代表用户一定在学习。
- Safari、Chrome 既可能用于查资料，也可能用于娱乐，必须结合“当前是否处于专注会话”和用户分类。
- 第一版只记录前台应用名称、Bundle ID、起止时间和用户分类；不读取窗口标题、网页地址、文档内容或键盘输入。
- 统计页应同时显示“主动计时”和“应用活动”，不自动覆盖用户确认的实际学习时间。

建议指标：

`专注纯度 = 专注会话内学习类应用秒数 ÷ 专注会话内所有被监测应用秒数`

### 2. 计划时间、实际时间和完成度可调整

完全合理，也是实际使用所必需的。忘记开计时、误计时和计划估算错误都会出现。

推荐保留一条轻量审计记录：修改前值、修改后值、修改时间和原因。手动校正不应触发奖励积分，否则积分容易失真。

### 3. 日、周、月统计图

合理。柱状图适合比较各模块的计划与实际时间，饼图适合看同一周期的时间构成，趋势折线适合观察节奏变化。

需要避免：

- 模块太多时仍强行使用饼图；超过 6 个模块时应把小项合并为“其他”。
- 只展示总时长而没有计划对照。
- 月视图堆积过多每日柱形；月视图应优先按周聚合。

### 4. DDL 与完成任务时的鼓励提醒

合理，但提醒必须克制：

- DDL 前 15 分钟提醒一次，到期提醒一次。
- 逾期任务进入汇总，不持续轰炸。
- 完成任务时弹出一句短鼓励，并提供立即关闭按钮。
- 鼓励语不使用羞辱、焦虑或“连续打卡即将断掉”式表达。
- 系统通知必须由用户主动开启。

### 5. 实时百分比

合理，但建议并列显示两个百分比：

- `任务完成度`：用户调整，范围 0–100%。
- `时间目标达成率 = 实际学习时间 ÷ 计划时间`：可以超过 100%。

当天总进度采用计划时间加权，防止一个 5 分钟小任务和一个 3 小时大任务权重相同：

`总体完成度 = Σ(任务完成度 × 任务计划分钟) ÷ Σ任务计划分钟`

### 6. 积分与奖励兑换

合理，尤其适合个人长期使用，但需要反刷分设计。不能简单按每学习一分钟无限给分，否则会鼓励拖长任务。

Demo 采用：

- 完成任务：+10。
- 至少提前 24 小时完成：额外 +5。
- 每日实际学习达到目标的 110%：+5，每日最多一次。
- 修改历史时间或完成度：不自动加分。
- 已经得分的任务即使恢复为未完成，再次完成也不重复得分。
- 兑换操作写入积分账本，并要求确认。

“一日休息券”应理解为提前安排的恢复日，而不是把未完成的紧急任务隐藏掉。

## Demo 验收范围

| 能力 | Demo 状态 | 说明 |
| --- | --- | --- |
| 添加、编辑、删除、完成任务 | 已实现 | 包括计划、DDL、实际时间和完成度 |
| 任务计时 | 已实现 | 页面打开期间实时运行，可暂停和恢复 |
| 应用使用统计 | 部分模拟 | 可分类、调整和采样当前页面；系统级统计留给原生版 |
| 日、周、月图表 | 已实现 | 柱状、饼图和趋势图 |
| DDL 与完成提醒 | 已实现 | 页面内提醒；系统通知需授权 |
| 实时进度 | 已实现 | 时间达成率与任务完成度分开 |
| 积分与兑换 | 已实现 | 含封顶、一次性计分与账本 |
| 每日笔记 | 已实现 | 本地自动保存并关联任务 |
| 跨设备同步 | 未实现 | 原生版建议使用 CloudKit |
| Apple Notes / Reminders / Calendar | 未实现 | 原生版接入 EventKit 与 Shortcuts |

## 建议的下一阶段优先级

1. 原生 macOS 菜单栏壳、SwiftData 数据模型和稳定本地通知。
2. 前台应用采样、空闲检测、专注会话上下文和隐私设置。
3. Reminders / Calendar 双向映射与冲突处理。
4. CloudKit 同步和 iPhone 小组件。
5. 在积累至少四周真实数据后，再决定是否加入自动排程或 AI 周报。
